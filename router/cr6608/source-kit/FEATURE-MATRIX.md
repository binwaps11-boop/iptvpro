# مصفوفة ميزات CR6608 Smart AP

هذه المصفوفة جزء من عقد الإصدار؛ كلمة «مدعوم» لا تعني أن الميزة استُخدمت
هوائيًا من عميل متوافق. الحالات هي:

- **متحقق حيًا**: قيس على راوتر CR6608 الهدف.
- **مبني ومختبر**: موجود في الصورة وله اختبار مصدر/إعداد، ويحتاج الاختبار الحي
  بعد التفليش عند اعتماده على WAN أو عميل آخر.
- **اختياري**: موجود لكنه لا يعمل قبل اختيار المستخدم؛ لا يجوز فرضه لأن ذلك قد
  يقطع عملاء أو يضر السرعة.
- **تأهيل RAM فقط**: مبني في صورة initramfs غير قابلة للبيع أو التفليش، ويحتاج
  إثباتًا حيًا مستقلاً قبل أي ترقية لحالة الدعم.
- **غير مدعوم عتاديًا**: لا يصح إظهاره كميزة ناجحة.

## القدرة وطبقة الراديو

| الميزة | الحالة الدقيقة |
|---|---|
| طلب الدرايفر/EEPROM shadow ‏38 dBm | **متحقق سابقًا على صورة المختبر المستقرة** كطلب درايفر/MCU على الراديوين، وليس كقياس قدرة RF. ملف `ul-lab` يعطّل مسار 38 dBm ويطلب 20 dBm فقط. اعتماد البيع ما زال يحتاج قياسًا conducted/radiated وحرارة وDFS والتزامًا تنظيميًا لكل سوق. |
| Wi‑Fi 6 / 802.11ax | **مبني ومتحقق وظيفيًا على المسار المستقر**؛ HE20 على 2.4G وHE80 على 5G. صورة v86 ذات mask 15 تحتاج إعادة إثبات هوائي وعدم ارتداد قبل اعتمادها. |
| 2×2 MIMO وSU‑MIMO وMRC | **مدعوم عتاديًا** في MT7915/لوحة CR6608؛ العميل ذو NSS1 سيبقى 1×1. |
| DL MU‑MIMO وExplicit/SU Beamforming | **مبني ومهيأ**؛ نشاط MU الفعلي يحتاج عدة عملاء متوافقين وقياسًا هوائيًا. |
| UL MU‑MIMO | **تأهيل RAM فقط في v86**. ملفا `lab` و`retail` لا يحتويان خاصية DTS الخاصة بـ UL‑MURU ويبقيان `cr6608_muru_mask=0`. ملف `ul-lab` غير القابل للبيع وحده يضيف بوابة DTS ويطلب mask 15، وbit 3 يفعّل طلب UL MU‑MIMO عبر `STA_REC_MURU` مع عداد نجاح استجابة الأمر فقط. عدادات الراديو المجمّعة ترابط زمني وليست إسنادًا للعميل؛ إثبات OTA يحتاج التقاطاً مناسباً أو telemetry لكل عميل. لذلك ليست دعماً رسمياً أو ميزة بيع. |
| DL‑OFDMA | **مدعوم ومهيأ/مدار من الدرايفر والفيرموير**؛ bit 0 في مسار MediaTek 25.12 مستقل، لكن جدولة airtime الفعلية مع عدة عملاء ما زالت غير مقاسة على v86. |
| UL‑OFDMA | **تأهيل RAM فقط في v86** عبر bit 1 من mask 15. نفس حدود upstream الخاصة بتعليق MT7915 ما زالت سبب الحصر في initramfs، ولا يرقى إلى دعم رسمي قبل إثبات عداد UL‑OFDMA مع عميلين، اختبار ضغط طويل، وRF/DFS/حرارة. |
| 1024‑QAM / HE MCS 0‑11 | **مدعوم**؛ اختيار MCS تلقائي حسب العميل والإشارة والتداخل. |
| BSS Coloring / Spatial Reuse / OBSS‑PD | **مهيأ**؛ الفائدة الفعلية تعتمد على بيئة BSS والعملاء. |
| TWT | MT7915 يعلن قدرة TWT؛ `he_twt_required=0` عمدًا حتى لا تُرفض أجهزة لا تدعمه. التفاوض يخص كل عميل. |
| LDPC / STBC / Rate Adaptation / SGI | **مهيأ/مدار من mac80211 وmt76**. |
| A‑MPDU / A‑MSDU / Frame Aggregation / Block ACK | **مدعوم في mac80211/mt76** ويُتفاوض عليه مع العميل؛ ليس زرًا ثابتًا. |
| 20/40/80 MHz / Dynamic bandwidth | **مدعوم**؛ 2.4G الافتراضي HE20 للاستقرار في الازدحام، و5G ‏HE80. |
| ACS / مسح التداخل / Noise floor / Channel utilization / CCA | **مبني** عبر iw/iwinfo/survey وخوارزمية القناة الآمنة؛ التبديل الليلي اختياري ومغلق افتراضيًا. |
| DFS / CAC | **مدعوم** في قنوات البلد التي تسمح به؛ زمن CAC لا يُتجاوز. |
| Background CAC | **مبني للوحة CR6608** بإزالة تعطيل DTS؛ قبول الصورة يتطلب أن يعلن `iw` قدرة `Radar background support`. التشغيل الفعلي يحتاج قناة DFS واختبار CAC منفصلًا. |
| Airtime Fairness / WMM / EDCA / MU‑EDCA | **مهيأ**؛ نتائج الجدولة تحتاج عملاء متزامنين. |

## التجوال والربط

| الميزة | الحالة الدقيقة |
|---|---|
| Smart Connect / Band Steering | **اختياري، مبني ومختبر مصدرًا**؛ يوحّد SSID والحماية على النطاقين ويستخدم usteer بسياسة محافظة. مغلق افتراضيًا كي لا يغيّر شبكة المستخدم. |
| Client balancing | usteer موجود، لكن الطرد العدواني معطل. قرار الانتقال النهائي بيد العميل. |
| 802.11k | **مهيأ** لتقارير الجيران. |
| 802.11v | **مهيأ بالطريقة الصحيحة `bss_transition=1`**؛ المفتاح القديم `ieee80211v` لا يُعتمد عليه. |
| 802.11r / Fast BSS Transition | **اختياري ومغلق افتراضيًا** بسبب مشاكل توافق موثقة مع بعض عملاء WPA3. لا يعمل مع شبكة مفتوحة. |
| 802.11s | يدعمه `wpad-openssl` وMT7915؛ التشفير المقبول في وضع mesh هو SAE أو open فقط. يحتاج عقدة ثانية لاختبار حي. |
| Ethernet Backhaul | **مدعوم** كجسر DSA/AP عادي. لا يجوز جمعه مع mesh في حلقة Layer‑2 بلا تصميم منع حلقات. |
| EasyMesh | **مضمن لكنه مغلق بسياسة آمنة** كـ prplMesh Controller + Agent + IEEE1905. يزامن Retail وQuick Settings بيانات fronthaul المشفرة داخل معاملتهما مع rollback كامل، من دون تمرير الأسرار في argv أو فتح بوابات الخدمة. فرض الأدوار، backhaul سلكي على `br-lan`، واشتراط fronthaul مشفر مختبرة تعاقديًا؛ لا توجد بعد شهادة تشغيل بين Controller/Agent حقيقيين أو تجوال بين عقدتين، لذلك لا يُعرض كدعم بيع مكتمل. |

## QoS ونقل البيانات

| الميزة | الحالة الدقيقة |
|---|---|
| SQM / CAKE / FQ‑CoDel | **مبني، اختياري**. لا يتفعل قبل اختيار واجهة WAN وإدخال سرعة خط مقاسة. |
| DiffServ4 / DSCP / Gaming QoS | ملف Gaming يضبط CAKE على DiffServ4. CAKE يحترم DSCP؛ لا يدّعي البناء معرفة كل لعبة تلقائيًا. |
| Per‑Host Fairness / Flow Isolation | ملف Gaming يستخدم `dual-srchost` للرفع و`dual-dsthost` للتنزيل مع NAT awareness. |
| ACK Filtering | ملف Gaming يفعله على الرفع فقط، حيث يفيد ولا يفسد تنزيل IFB. |
| Ingress/Egress shaping / Bufferbloat | **مدعوم** عبر SQM/IFB؛ تعطَّل flow offload تلقائيًا عند تشغيل SQM حتى تمر الحزم في qdisc. |
| ECN | **مفعل في ملف CAKE Gaming**. |
| حد سرعة لكل جهاز | **مبني** كـnftables bridge policer مستقل عن SQM، مع استرجاع السياسة السابقة إذا فشل التطبيق. |
| Device priority / Traffic classification | الأولوية المبنية هي DiffServ/DSCP. التصنيف العشوائي حسب أسماء التطبيقات غير مفعل لأنه غير موثوق مع QUIC/VPN والتشفير. |

## IP والخدمات والأمان

| الميزة | الحالة الدقيقة |
|---|---|
| IPv4 / IPv6 | **IPv4 فقط بسياسة ثابتة**؛ WAN IPv6 وRA وDHCPv6 وprefix delegation معطلة، مع إبقاء دعم kernel الداخلي لاستقرار loopback/nft. |
| NAT‑PMP / PCP / UPnP | `miniupnpd-nftables` وLuCI مضمنان، لكن الخدمة **مغلقة افتراضيًا** ولا تُفتح بلا WAN يملكه الراوتر. |
| Port forwarding | مدعوم عبر firewall4/LuCI عند وضع الراوتر؛ لا يوجد تحويل منفذ افتراضي. |
| WPA2‑AES / WPA3‑Personal / SAE / PMF 802.11w | **مدعوم** في `wpad-openssl`، مع PMF صحيح لكل وضع. الشبكة النظيفة لا تُفرض عليها كلمة مرور مجهولة للمستخدم. |
| OWE | **مبني** كخيار Guest مشفر بلا كلمة مرور مع PMF إلزامي. OWE لا يثبت هوية AP ولا يمنع Evil Twin. |
| Client isolation / Guest network | **مبني**؛ Guest routed لا يُنشأ في AP mode بلا WAN، كي لا ينتج «متصل بلا إنترنت». |
| VLAN / DSA / WAN | **مبني ومختبر تعاقديًا**؛ يدعم PPPoE على `wan` العاري (غير موسوم)، وPPPoE فوق 802.1Q عبر جهاز `wan.<VID>` مملوك صراحةً مع VID من 1 إلى 4094، مستقل عن VLAN ‏LAN/AP. أداة الجاهزية لا تغيّر PHY أو UCI، وتفحص عضوية `br-lan` وcarrier والعدادات وVLAN وملكية WAN، وترفض التعارض مع واجهة أو جهاز أو bridge آخر. ما زال يلزم اختبار كابل/ISP فعلي، وحمل ثنائي الاتجاه، وقياس السرعة والأخطاء على كل منفذ قبل اعتماد البيع. |
| Multi‑PSK | يدعمه OpenWrt عبر `wifi-station`/`wpa_psk_file`. لا توجد مفاتيح افتراضية؛ VLAN لكل PSK يحتاج شبكة/DHCP/firewall كاملة واختبار عملاء قبل اعتماده. |

## الثبات والواجهة

- جلسات Smart AP وLuCI محدودة زمنيًا، وعمليات ubus المقيدة لا تستطيع تعليق CGI بلا نهاية.
- كل طلبات `dashapi2` حية حتى عند غياب `live=1`: لا تُنشئ أو تقرأ ملفات telemetry
  قابلة لإعادة الاستخدام. حارس صغير هو الوحيد الذي يحتفظ بـ`FD8`؛ والد CGI يغلقه
  قبل تشغيل أي جامع فرعي، والحارس يراقب هوية الوالد (`PID+starttime`) ويحرر
  `collector.lock` عند موته. ملفات عزل الأوامر تُحذف طبيعيًا، وبعد `SIGKILL` يفصل
  أول مالك تالٍ أسماء كل البقايا قبل الجمع. إذا كان ابن قد فتح inode خاصًا بالطلب
  قبل موت الوالد فقد يبقى ذلك الـinode المحذوف بلا اسم، ويقبل كتابة متأخرة عبر
  الواصف المفتوح فقط، إلى أن يغلقه الابن؛ لا يمكن الوصول إليه بالمسار ولا تعيد
  الكتابة المتأخرة إنشاء الملف. لذلك الضمان هو **صفر telemetry قابلة للوصول أو
  لإعادة الاستخدام بعد الاسترداد**، وليس محو inode مفتوح قسريًا من النواة. عند
  السكون لا تبقى قياسات أو استجابات محفوظة؛ تبقى بيانات التنسيق فقط.
- الواجهة لا تقرأ `localStorage` أو `sessionStorage` ولا تنشئ فيهما أي قيمة؛ حالة
  العرض مؤقتة في ذاكرة الصفحة فقط. عند `pagehide` تُمسح اللقطة والسجلات وحقول
  التحكم وكلمة المرور ووظائف الرسم، وإذا أعاد المتصفح وثيقة من bfcache تُحمّل
  الصفحة من جديد وتتحقق من جلسة HttpOnly قبل أي لقطة حية. عند فتح الصفحة ينفذ
  ملف ترحيل حذفًا خاملًا
  لمرة واحدة في عمر الصفحة لمفاتيح Smart AP التاريخية الدقيقة فقط: مفاتيح
  `localStorage` هي `smartap.availability`, `cardOrder`, `dailyBudgetGb`,
  `dayBaseRx`, `dayBaseTx`, `devNames`, `events`, `histories`,
  `insightCategory`, `interval`, `knownMacs`, `lang`, `latHist`,
  `monthBaseRx`, `monthBaseTx`, `monthBudgetGb`, `outageLog`, `theme`,
  `themePref`, `uiVersion`, `weeklyLog`, `yearBaseRx`, و`yearBaseTx` (كلها
  تحت البادئة `smartap.`)، ومفتاح `sessionStorage` الوحيد هو
  `smartap.session`. لا يوجد مسح بالبادئة أو `clear()` ولا تُكتب علامة اكتمال؛
  لذلك تبقى المفاتيح غير التابعة للتطبيق، حتى داخل `smartap.*`، بلا مساس. كل
  استجابات الملفات الثابتة وlogin/API/actions والقياسات الحية تحمل `no-store`؛
  Cookie الدخول Session-only بلا `Max-Age` مع انتهاء خادمي رتيب بعد ساعة.
- إحصاء Bitrate معروض باسم **آخر PHY TX/RX rate، وليس throughput**، مع
  MCS/NSS/GI/width/retries/failures.
- EEE معطل مبكرًا في MT7530/MT7621. قياس سابق أثبت LAN1 ‏1 Gbps Full Duplex،
  لكن لقطة 2026-08-27 الحالية تفاوضت على 100 Mbps فقط مع drops قليلة؛ لذلك يلزم
  استبدال الكابل/الطرف المقابل وإعادة اختبار Gigabit قبل اعتماد النقل.
- الاختبار الصحي لا يعيد تشغيل الجهاز أو المنافذ؛ يراقب DSA/Wi‑Fi/العمليات
  الأساسية ويترك الإصلاحات المسببة للفصل لقرار واضح.

## حدود إصدار v86

- `lab`: مرشح مختبر غير قابل للبيع، mask 0، شبكة افتراضية مفتوحة، ومسار طلب
  38 dBm يحتاج تحقق RF خارجيًا.
- `retail`: صورة عامة غير مهيأة، الراديو مقفل، mask 0، ولا توجد بيانات دخول
  مشتركة فعالة؛ تبقى `sale_ready=NO` حتى تهيئة بيانات فريدة وفحوص الجهاز والسوق.
- `ul-lab`: صورة `initramfs` للإقلاع من RAM فقط، mask 15 وطلب 20 dBm؛ لا ينشر
  البناء لها sysupgrade أو combined firmware.
- لا تصبح أي صورة جاهزة للبيع قبل اكتمال OTA متعدد العملاء، EasyMesh بعقدتين،
  اختبار كل المنافذ بالحمل، soak/حرارة/إعادات تشغيل طويلة، واعتمادات RF/DFS
  والتنظيم لكل سوق. الاختبارات المصدرية أو نجاح البناء وحدهما لا تزيل هذه الحواجز.
